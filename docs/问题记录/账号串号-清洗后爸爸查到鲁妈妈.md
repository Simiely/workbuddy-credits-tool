# 账号串号:清洗 cookie 后"爸爸"查到"鲁妈妈"的数据

## 现象

2026-08-06 修复 400 Cookie Too Large 后,仪表盘显示"爸爸"账号的积分与"鲁妈妈"完全一致;全量校验发现 **爸爸(登记 Uin 330105530346)查询返回的是 330105610813(鲁妈妈)的数据**。鲁妈妈自身正确。

## 排查

1. 实测当前 cookie:爸爸查询接口返回 `Accounts[].Uin = 330105610813` → 爸爸的 cookie 实际是鲁妈妈的会话。
2. 对比备份(`credits.db.bak-20260806`,清洗前):**会话 `c4c93b98` 同时出现在爸爸和鲁妈妈的原始 cookie 里**;爸爸原始 cookie 有 2 个 `session`(MMFetyr=爸爸 / lrzBzBr=鲁妈妈)和 2 个 `AUTH_SESSION_ID`(5aa6d8a2 / c4c93b98)。
3. 根因:`sanitizeCookieHeader()` 同名去重"保留最后一份",把爸爸记录里**最后一个** session(lrzBzBr,鲁妈妈的,时间更晚)保留、把爸爸自己的 MMFetyr 丢弃 → 爸爸的凭证组合变成了鲁妈妈的会话。
   - 深层原因:edge-daemon 旧版 `getAllCookies` 采集时把**多套登录会话**混进了同一个账号记录(用户多次登录/换账号的残留 cookie 全拼一起)。

## 修复

1. **数据修复**:暴力测试爸爸原始 cookie 的会话组合(IDENTITY×session×AUTH×session_2 笛卡尔积),命中唯一返回 Uin=330105530346 的组合:
   `KEYCLOAK_IDENTITY + session=MMFetyr...`(带 session_2 亦可)。更新两处 credits.db(积分监控/ + 项目根)。
2. **全量校验**:6 个账号逐个查询,比较接口返回 Uin 与登记 Uin —— 仅爸爸异常,其余 5 个正确。
3. **历史清理**:串号期间(08-06 00:48~01:29 UTC)爸爸的 10 条快照实为鲁妈妈数值,已删除(备份 `credits.db.bak-clean-dad`);8/5 及更早 165 条历史经同时刻对比全部正常,未动。
4. **代码防护**(`src/compute/query.js`):新增 `assertOwner()` —— 查询结果 `Accounts[0].Uin` 与账号登记 Uin 不一致时抛错("账号串号..."),**不写入历史**,避免再次污染;`fetchAllAccounts` / `fetchOneAccount` 均接入。

## 教训 / 后续

- 采集端已治本(`Network.getCookies(urls)` 精确采集),新添加的账号不会再混会话。
- 对历史脏数据,**同名去重不足以保证正确归属**,必须以"接口返回 Uin == 登记 Uin"校验。
- 排查工具:全账号 Uin 归属校验脚本(遍历 accounts,逐个请求接口比对 Uin);会话组合暴力测试脚本(备份原始 cookie 上笛卡尔积查询)。
- 若再遇类似串号:从 `credits.db.bak-*` 恢复原始 cookie → 组合测试 → 更新 cookieHeader → 删除串号期 readings。
