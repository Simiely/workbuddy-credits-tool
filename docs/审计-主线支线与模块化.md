## 1. 主线逻辑（清晰，值得保留）

管线隐喻在代码里是名副其实的：

```
采集 collect/ ──► 查询 query ──► 时序存储 store/db(readings, append-only)
                                      │
                          采样 scheduler(周期写 readings)
                                      │
                          派生 derive(纯函数) ──► 告警 alerts(纯函数) ──► 展示/CLI
```

- `src/compute/derive.js`、`alerts.js`、`model.js` 都是**纯函数、无副作用、单数据源**（只读 readings）。这是全项目最干净的部分。
- `domain.js` 用 typedef 定义了四实体词汇表（Account/Reading/Derived/Alert），方向正确。
- `config.js` 集中常量 + 环境变量（采集方案、告警阈值、管理员密码）。
- 单一真相源：`credits.db`（accounts + readings），旧散 JSON 仅作 WebDAV 镜像桥接。

**主线结论**：这条主干没有问题，重构 P0–P4 的"派生收口 / 告警收口"是成功的。

## 2. 支线逻辑（缠绕点）

### 2.1 🔴 [高] WebDAV 上传/下载路径运行期报错（真实缺陷）

`wb-gui.mjs` 第 406/431 行直接调用 `exportLegacy()` 与 `importLegacy()`，但这两个名字**并未在作用域内绑定**：

- 第 28–29 行：`import { exportLegacy as exportHistory, importLegacy as importHistory } from history.js`
- 第 10–16 行导入 `store.js` 时**没有**带 `store.js` 的 `exportLegacy/importLegacy`。

ESM 里 `import { A as B }` 只绑定 `B`，不绑定 `A`。于是：
- 第 406 行 `exportLegacy()` → **ReferenceError（未定义）**，WebDAV 上传直接崩溃；
- 第 431 行 `importLegacy()` → 同理崩溃。

后果：本应"先导出账号池镜像、再导出历史镜像"的上传，第 1 步就抛错；且账号池镜像（`wb-accounts.json`）**从未被连到上传流程**（注释写"导出账号池"但接的是 history 的别名）。下载同理。我们此前只测了 `webdav/test`，未触发该路径，故一直漏掉。

> 修复：明确区分两套 legacy 桥接。`store.js` 的 `exportLegacy/importLegacy` 负责账号池，`history.js` 的负责 readings。路由里应分别 import 两个非冲突名字（如 `exportAccountsLegacy` / `exportReadingsLegacy`），再在 upload/download 里各调一次。

### 2.2 ⚠️ [中] 路由层是 498 行平铺 if-chain，主线/支线全混在一起

`wb-gui.mjs` 的请求处理器是一个巨型 `if (url.pathname === ...)` 链，读类（status/accounts/dashboard/all/derived/alerts/stream）与写类（save-current/rename/del/reorder/clear-data/webdav/*/scheduler/set）**无任何结构区分**。

- 管理员鉴权 `requireAdmin(...)` **机械重复 11 次**（第 299/308/320/332/360/386/398/404/420/438/453 行），每条写接口前各贴一句。
- 没有"方法+路径"路由表、没有中间件、没有控制器分层。新增一个接口=在链里再插一段 if。

**期望形态**：路由表 `routes = [{method, path, handler, admin:true}]` + 一个 `requireAdmin` 中间件统一拦截。主线（只读派生视图）与支线（写操作）在结构上即可一眼区分。

### 2.3 ⚠️ [中] 前端"双数据源"手工对账，是支线最乱处

前端同时维护两份数据：
- `S`（`/api/all` 实时查询，含 `data.Accounts` 原始结构）→ 驱动 hero 卡、账号卡、明细弹窗；
- `dashPer`（`/api/dashboard/all` 派生视图）→ 驱动总览表、趋势图、告警。

在 `renderDashTable()` 里把两者硬拼：`credMap`/`expMap` 从 `S.results` 取（凭证状态、赠送包过期），其余字段（todayUsed/used/alerts）从 `dashPer` 取。一处刷新时机错位，就可能出现"剩余是新的、过期列是旧的"。

### 2.4 ✅ [已解决] "单派生源"漏点：赠送包过期 & 明细桶已收口(③)

P2–P4 把 todayUsed/dailyRate/daysToEmpty/告警都收口到后端 `derive.js`/`alerts.js`；**赠送包过期日历**与**明细弹窗的到期桶**原本是前端从 `r.data.Accounts` 原始数据现算（旧 `wb-gui.js:196 expiringInDays()`、`211 buildExpiryMap()`、`649 buildBuckets()`、`669 renderBuckets()`）。

现已收口：
- 赠送包过期口径在后端 `src/compute/derive.js` 的 `deriveGiftExpiry()`（单派生源），由 `buildSnapshotEntry()` 把子账号列表持久化进 readings 后派生；`/api/dashboard/all`、`/api/derived` 返回的 `expiring1d/expiring3d/giftBuckets/expiryTier` 即此口径，前端表格/hero/明细柱/排序全部消费派生结果（不再从 `r.data.Accounts` 现算）。
- 明细桶 `renderGiftBuckets()`（原 `renderBuckets`）在前端 `wb-gui.render.js` 纯渲染，数据来自后端派生。

后果已消除：凭证过期（alerts）与赠送包过期（derive）口径统一到后端一处，可统一测试。

### 2.5 ⚠️ [中] `/api/all` 把"查询"和"采样"揉在一起

`/api/all`（第 193 行）既实时查询、又把结果 `appendSnapshot` 写入 readings。于是"查询(Query)"与"采样(Sampling)"是同一个动作（用户点刷新 = 采一次样）。后台调度器 `scheduler.runOnce` 也写 readings。两条写入路径没有共享的"采样器"抽象，靠"用户刷新"和"定时器"各自独立 append。

设计上，采样应只有**一个入口**（如 `sampleAll()`），被"手动刷新"和"调度器"共同调用；`/api/all` 只负责"查实时 + 顺带采样"，语义应显式而非顺手写入。

### 2.6 🟢 [低] 命名 / 结构小瑕疵

- `src/compute/store.js`（账号池仓库）与 `src/store/db.js`（SQLite 连接）都叫 "store"，初看混淆。
- `history.js` 的 `buildDashboard()` 已死（第 118 行，无任何调用方，被 `getDerived()` 取代）；`store.js` 的 `exportLegacy/importLegacy` 服务端未接线（只有 history 版被 webdav 用到）。
- `wb-last-data.json` 镜像仍被 `saveLastData/loadLastData` 读写，但 readings 已是真相源，此镜像属冗余遗留。
