# 时区分析教训：浏览器时区 ≠ 进程时区（前端"本地时区"并非都要改 +8）

> **TL;DR**:后端进程时区(Docker UTC)≠ 浏览器时区(用户电脑 +8)。v1.4.29/30 修后端后,「浏览器 +8 访问容器后端」形态下前端本地时区计算与后端 +8 口径**完全自洽**——前端"昨日键/图表归日"用浏览器本地时区是**正确**的,不要盲目改成 +8。只有当浏览器自身时区 ≠ +8(跨时区访问)才需要前端配合。模拟浏览器时区必须用「+8 平移 + getUTC*」,不能 `new Date()` + `getFullYear`(那是进程时区)。

## 背景（2026-08-08 排查 v1.4.45 时）

对项目做优化排查,初判前端三处"残留本地时区"要改成 +8:
1. `renderHero` 昨日已用基准键(`new Date()` 减一天)
2. `chart.js` 的 `dayZero()`/`dayWindow()`(数据点归一化)
3. `wb-gui.mjs` dashboard 缓存键 `new Date().toDateString()`

用户质疑:「时区是因为路由器和电脑的计算方式不同,会不会你的修改意见是错的」。

## 验证（真实部署形态）

模拟**后端进程 TZ=UTC + 浏览器 +8**:48 个时刻的昨日键 + 4 个跨日临界快照归日,**全部一致(52/52)**。

为什么一致:
- 后端 `derive.js` 归日 = `new Date(ts + 8h).getUTC*`（cnWall 平移法）
- 浏览器(+8) `new Date(ts)` 的本地年/月/日 = `ts + 8h` 取 UTC 字段 —— **两者算法等价**
- `renderHero` 昨日键:浏览器 +8 下 `new Date()` 减一天 == 后端 +8 昨天
- v1.4.29/30 把后端从"进程时区"改成"固定 +8"后,前端(浏览器 +8)天然对齐,**无需再改前端**

只有「浏览器时区 ≠ +8」(如跨时区访问 NAS 上的实例、浏览器手动改时区)才会错,属防御性场景。

## 教训（两条）

1. **判断前端时区 bug 前,先确认浏览器时区**。前端跑在浏览器,时区 = 用户设备时区,与后端进程时区无关。桌面 +8 用户 + 容器 UTC 后端 = 自洽,别再动前端。
2. **模拟浏览器时区的方法**:`new Date(ts)` + `getFullYear/getMonth/getDate` 在 Node 里是**进程时区**,不是浏览器时区。要模拟浏览器 +8 必须用 `new Date(ts + 8*3600e3)` + `getUTC*`(与后端 cnWall 同法)。本次初版验证脚本用错方法,得出"16/48 不一致"的假结论;修正后 48/48 一致。

## 结论（v1.4.45 未改前端时区）

- 前端三处"本地时区"保持现状(用户真实场景正确)
- dashboard 缓存键 `toDateString()` 虽有进程时区依赖,但主失效驱动是 `latestReadingTs()`(/api/all 先写新快照再请求 dashboard,必然刷新),实际无影响
- 性能"批量读取"经基准(14.4ms vs 22.5ms)证伪,不做
- 唯一确认的真 bug:前端 innerHTML 注入未转义(XSS),已修(见 v1.4.45)
